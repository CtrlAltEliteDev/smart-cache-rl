Where the data comes from

Everything in the Response panel is JSON returned by this page’s own origin: the Smart Cache RL FastAPI server (/reset, /step, /state, /schema, /metadata). There is no separate database in the UI; you are looking at live environment output.

Observations are built inside SmartCacheRlEnvironment: cache slots, the next request, rewards, and metadata (hit rate, step count, catalog source, Redis status). The request stream is sampled from an internal popularity model. If USE_WIKIPEDIA_DATA=true, item popularity can come from Wikimedia pageviews (REST API); otherwise the catalog falls back to synthetic data. Optional Redis (USE_REDIS, REDIS_URL) mirrors episode metrics for monitoring; the chips show connection status when present.

How it works

The environment simulates a fixed-size cache under a stream of item requests. Each Step applies your JSON action: manual eviction index, or let an agent pick (lru, lfu, or dqn). Rewards reflect hits and misses (and penalties on invalid moves). Reset starts a new episode; Get State / Schema / Metadata introspect current state and types without advancing time.

  • Use the textarea to send a SmartCacheRlAction (for example use_agent and agent_mode).
  • The metric chips update from the latest payload’s observation and metadata.

Why this app and the real world

Compared to fixed eviction rules, reinforcement learning lets you explore policies that adapt to skewed traffic and cost signals, similar in spirit to CDN edge caches, application caches, and key-value tiers where admission and eviction affect latency and load. This UI is a controlled lab: same APIs you would use from scripts or MCP, with clear JSON for debugging.

In production, operators still rely on heuristics and SLAs; here you can compare LRU/LFU/DQN on the same workload, inspect hit rate and rewards per step, and optionally export metrics to Redis like you might to a time-series or dashboard in the real world.

Eviction challenge

Keep hot items in the cache. To choose a victim slot: wait until the hint says the cache is full and the next request is a miss, then click one occupied slot (that slot is evicted), then press Step. On a hit, or when a free slot exists, you do not pick a victim. Scenarios match README tasks; align server env vars for fair benchmarks.

To clear the whole cache (wipe all slots): that is only possible with New round — it runs /reset and starts a new episode with an empty cache. There is no “delete all slots” or “clear LRU list” button. Each Step is one request; on a full-cache miss you evict only one victim at a time.

User guide

Side navigation

The Current view box under the tabs always shows whether you are in Playground or Dashboard. The active tab has a teal bar on the left and filled background.

  • Playground — hands-on eviction game: choose a scenario, start a round, pick slots when needed, and see how your choice compares to LRU and other hints.
  • Dashboard — developer tools: send JSON actions, read the full API response, and run policy comparison.

Playground

  1. Pick a Scenario (task goal and step target).
  2. Click New round to start an episode.
  3. Read Incoming request and whether the next step is a hit or miss.
  4. If the cache is full and the request is a miss, use the big Your eviction slot panel above the grid: it shows Not selected yet until you click a slot, then it displays Slot N. Press Step to apply.
  5. Read the feedback line after each eviction to compare your slot to baselines.

Dashboard

  1. Edit Step Action JSON and use Reset, Step, and the other API buttons.
  2. Inspect the Response panel for raw JSON.
  3. Use Run Comparison to benchmark LRU, LFU, and DQN on the same step count.
